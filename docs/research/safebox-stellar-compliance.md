## 1. Group Savings (Safebox) — Compliance Basics

### What PayFlex built
Safebox is a shared, transparent pool: any member can deposit funds, but
only the owner and designated admins (capped at 3) can withdraw. The
pool is tracked in-app by PayFlex; the actual money sits in a BMONI smart
wallet owned by the pool creator.

### Regulatory category risks

**E-Money / Stored Value**
- Pooling member funds into a single wallet controlled by one person
  (the Safebox owner) looks like accepting deposits on behalf of others.
- In Nigeria (CBN regulations), the UK (FCA EMR 2011), and most
  jurisdictions, collecting money from third parties and holding it in a
  pooled account requires at minimum a payment services license or a
  passthrough exemption.
- **Mitigation currently in place:** BMONI Embedded is the underlying
  licensed rail. PayFlex should confirm with BMONI's compliance team that
  the Safebox pattern (pooled wallet, third-party contributions) is
  explicitly covered by BMONI's own license/scheme rules, not just assumed.

**KYC on Members**
- Safebox members contribute money but are currently only identified by
  a userId or email — there is no enforced KYC step for members before
  they contribute.
- If the pool exceeds relevant thresholds (e.g. NGN 500k aggregate in
  Nigeria, £10k in the UK), member-level KYC becomes a likely regulator
  expectation.
- **Recommended: gate contributions at or above a threshold on member
  KYC status, using the existing KYC level in the BMONI user record.**

**AML / Unusual patterns**
- A Safebox with many contributors depositing small amounts and one
  person withdrawing the aggregate is structurally similar to structuring.
- Implement and log velocity checks: flag safeboxes where single-session
  net contributions exceed platform transaction limits, even if individual
  contributions don't.

**Transparency / Audit trail**
- The SafeboxTransaction ledger (already implemented) is good. Ensure
  it's append-only at the database level (no UPDATE/DELETE on transaction
  rows) and that withdrawal notes are mandatory — the current UI already
  enforces this but the backend DTO should mark `note` as non-optional
  for WITHDRAWAL type.

### Hard boundaries to keep
- 3-admin cap is correct — limits the blast radius of a compromised admin.
- Owner-only transfer: the current "no ownership transfer" design avoids
  a whole category of disputes. If ownership transfer is ever added, it
  should be a 2-step, 24h delay confirmation (as the original spec noted).
- Never expose raw wallet addresses or private keys to non-owner members.

## 2. Parallel Stellar Rail — What a Real Integration Would Need

**This section is preparatory. No Stellar code should be written until
the repo link is provided and a dedicated prompt authorizes the work.**

### What Stellar's architecture means for this app

Stellar is a Layer-1 blockchain (not EVM). Its Soroban smart contract
platform is the relevant surface for integrating with a counterparty
contract. Key differences from BMONI Embedded:

| Property | BMONI Embedded | Stellar / Soroban |
|---|---|---|
| Transaction reversibility | BMONI can void/reverse | On-chain: irreversible once finalized |
| Settlement time | Near-instant (centralized) | ~5s (Stellar consensus) |
| Key management | bmoni_embedded_sdk on-device | Separate Stellar signing key needed |
| Fees | Platform fee, variable | Lumens (XLM) base fee, very low |
| KYC bridge | Native via BMONI | Must be re-bridged at app level |
| Auditability | BMONI ledger + PayFlex DB | Public Stellar ledger + PayFlex DB |

### Key integration concerns

**1. Key management**
- BMONI uses an EVM secp256k1 key (generated by bmoni_embedded_sdk).
- Stellar uses ED25519 keys. These cannot be derived from the same seed
  unless a specific KDF is agreed with the Stellar contract author.
- Options: (a) derive a Stellar key from the BMONI seed in-device using
  a known derivation path (requires SDK support); (b) generate a separate
  Stellar key and store it in the device secure enclave alongside the
  BMONI key; (c) use server-side custody (worst option — moves trust to
  the server).
- **Do not attempt key management until the contract author specifies
  which key type and derivation path they expect.**

**2. KYC bridging**
- Stellar accounts can be activated by the contract or by the user
  funding a minimum XLM balance (~1 XLM base reserve).
- If the Stellar contract requires a KYC attestation (common for
  regulated asset issuance via SEP-0008), PayFlex will need to have
  BMONI's KYC data signed in a format the Stellar contract accepts.
- If the contract is permissionless, KYC is PayFlex's own responsibility:
  gate Stellar operations on the same KYC level the app already tracks.

**3. Irreversibility**
- Users must see a prominent, unambiguous warning before any on-chain
  Stellar transaction: "This payment cannot be reversed once sent."
- The existing PfPaymentConfirmationSheet is a good host for this —
  add a red-bordered irreversibility disclaimer panel when the payment
  route is Stellar (not shown for BMONI rail).
- Implement double-confirmation for amounts above a threshold (e.g. any
  Stellar transaction > NGN 100k should require PIN re-entry even mid-flow).

**4. Fee display**
- Stellar base fees are tiny (currently ~100 stroops = 0.00001 XLM) but
  the app must display an estimated fee in the user's local currency
  before submission. Fetch from Horizon fee_stats endpoint at time of
  review, not hardcoded.

**5. Settlement record sync**
- After an on-chain transaction confirms (poll Horizon or subscribe to
  SSE), write the result back to the PayFlex Transaction table (or a
  new StellarTransaction table) with the Stellar transaction hash as a
  non-nullable reference.
- Never mark a Stellar-routed PayFlex transaction as SUCCESS until the
  on-chain confirmation is received. Use PENDING_CHAIN as an intermediate
  status.

**6. Safebox x Stellar interaction**
- If a Safebox withdrawal is routed over Stellar, the irreversibility
  rules above apply doubly: the withdrawal note is mandatory AND the
  member must confirm the destination is correct and that the transaction
  is irreversible.
- Consider whether Safebox should support Stellar routing at all in v1,
  or whether it's BMONI-only until the pattern is proven.
